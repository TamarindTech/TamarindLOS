## 1. Purpose

Every capability in Tamarind is a **tool**. A tool is defined once, in YAML, and that definition generates:

- the REST endpoint and OpenAPI document,
- the MCP tool exposed to agents,
- Go server stubs and Python / TypeScript client types,
- the gateway's validation, policy and autonomy configuration.

## 2. Definition format

Tools are grouped by domain in catalogue files under `tools/catalogue/`. Each file is validated against `tools/schema/tool-definition.schema.json`.

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | `domain.verb`, e.g. `document.request`. Stable public identifier. |
| `version` | yes | Semantic version of the contract. Breaking input/output changes require a major bump. |
| `summary` / `description` | summary | Shown to humans and to agents. Write for an agent deciding whether to call the tool. |
| `risk_tier` | yes | `read`, `low`, `medium`, `high`. Drives default autonomy, audit depth and approval rules. |
| `default_autonomy` | yes | `L0`–`L4`, or `gate` (always needs a human approval). |
| `max_autonomy` | no | Upper bound no tenant or pack may exceed, e.g. `offer.accept` is fixed at `L0` because only the borrower can accept. |
| `mutates` | yes | Whether the tool changes state. Read-only tools never need approval. |
| `idempotent` | yes | Whether repeating the call with the same idempotency key is safe. |
| `scopes` | yes | OAuth-style scopes the caller must hold, e.g. `checks:run`. |
| `consent` | no | Consent scopes that must be valid for the party, e.g. `credit_bureau`. Missing consent fails with `CONSENT_MISSING`. |
| `preconditions` | no | CEL expressions over the application snapshot, checked before execution. |
| `transition` | no | State-machine transition the tool performs (`from` → `to`). |
| `emits` | no | Domain events written to the event log on success. |
| `errors` | no | Typed error codes the tool can return. |
| `input` / `output` | yes | JSON Schema for the payloads. |

### Conventions

- **Identifiers** are UUIDs (UUIDv7 generated by the core).
- **Money** is always `*_minor` integers (e.g. cents) plus an ISO 4217 `currency`. Never floats.
- **Rates** are basis points (`rate_apr_bps: 1900` = 19.00% APR).
- **Timestamps** are RFC 3339 in UTC.
- **Enums** are lower snake case.

## 3. Invocation envelope

Every call, whether through REST or MCP, carries an envelope in addition to the tool input:

| Field | Required | Meaning |
|---|---|---|
| `idempotency_key` | for mutating tools | Unique per actor and tool. A repeated key returns the original result. |
| `expected_state_version` | for transitions | Optimistic concurrency. A mismatch returns `STATE_CONFLICT`. |
| `dry_run` | no | Check authorization, preconditions and policy without executing. |
| `reason` | for agents | Why the agent is calling the tool. Stored in the audit trail. Enforced in the database. |
| `on_behalf_of` | for delegated calls | The user or organisation the actor represents. |
| `trace_id` | no | W3C trace ID that links agent runs, tool calls and connector calls. |
| `run_id` | agents, inside a run | The agent run (`agent.run_start`) the call belongs to. Only the agent that opened the run may use it; changes are refused once the run is closed. |

## 4. Gateway processing order

1. Authenticate the actor and resolve `on_behalf_of`.
2. Validate input against the tool's JSON Schema.
3. Check the idempotency key; return the stored result on a repeat.
4. **Authorize with Cedar**, for the actor and, when delegated, for the represented principal. Both must be allowed.
5. Load the application snapshot and evaluate **CEL preconditions**.
6. Check **consent** where the tool declares it.
7. Resolve **effective autonomy**: the lowest of the tool's `max_autonomy`, the tenant setting, the policy pack setting and the actor's trust level.
   - `gate` → create an approval request and return `APPROVAL_REQUIRED`.
   - `L2` for an agent → store the call as a proposal for human confirmation.
8. Execute in one database transaction: state change, events and outbox rows.
9. Record the invocation (actor, principal, reason, policy result, outcome) in `tool_invocations`.

## 5. Error codes

| Code | Meaning | Typical agent response |
|---|---|---|
| `VALIDATION_FAILED` | Input failed schema validation | Fix the input |
| `NOT_FOUND` | Referenced object does not exist or isn't visible | Re-read state |
| `STATE_CONFLICT` | State changed since the caller read it | Re-read and retry |
| `PRECONDITION_FAILED` | A CEL precondition is false (details list which) | Call `application.next_actions` |
| `CONSENT_MISSING` | Required consent absent or expired | Request consent from the party |
| `POLICY_DENIED` | Cedar denied the action | Stop; escalate to a human task |
| `APPROVAL_REQUIRED` | Action is gated; an approval request was created | Wait for `ApprovalGranted` |
| `APPROVAL_LIMIT_EXCEEDED` | Amount exceeds the approver's authority | Refer to a higher authority |
| `MAKER_CHECKER_VIOLATION` | Same person recommending and approving | Route to a different approver |
| `PROVIDER_UNAVAILABLE` / `TARGET_UNAVAILABLE` | External system down | Retry later; the gateway applies backoff |
| Tool-specific | e.g. `MALWARE_DETECTED`, `OFFER_EXPIRED` | See the tool definition |

## 6. Mapping to interfaces

| Interface | Mapping |
|---|---|
| **REST** | `POST /v1/tools/{name}` with `{ "input": {...}, ...envelope }`. Read tools also get `GET` routes, e.g. `GET /v1/applications/{id}`. |
| **MCP tools** | Each tool is exposed with dots replaced by underscores (`application.create` → `application_create`), because several MCP clients only accept `[a-zA-Z0-9_-]` in tool names. Only tools the caller holds scopes for are listed. Envelope fields go in the tool arguments under `_envelope`. See [ADR-0005](../adr/0005-mcp-server-phase-0.md). |
| **MCP resources** | `tamarind://applications/{id}/snapshot`, `tamarind://applications/{id}/decision-records`, `tamarind://products/{code}/policy` |
| **Events** | Each `emits` entry is a domain event, written in the same transaction as the state change. Subscribers read the tenant's events in order from `GET /v1/events?after={seq}&types=...&wait={seconds}` (scope `events:read`); with `wait`, the request long-polls and wakes when a new event commits (PostgreSQL `NOTIFY`). Outbound webhooks are planned on the same outbox. |
